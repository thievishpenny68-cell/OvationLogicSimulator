# 多项相消的精确算式核对

0.37.0/引擎0.27.0，为SUM、QAVERAGE、POLYNOMIAL增加一个精确公式参考，保留已有分阶段Float32和binary64核对。**参考只用于拒绝不确定工况，不替代原输出，也不声称Ovation采用精确算式运算。** 引脚、参数、初态和扫描顺序不变。

## 为什么需要

当输入为`[2^100, 1, -2^100]`时，原分阶段Float32和顺序binary64求和都会丢掉1并得到0。SUM数学公式应为1，QAVERAGE为1/3；POLYNOMIAL在x=1、前三系数为同样三数时也有该问题。小量藏在某一路偏置中时，单纯补偿最终各路之和也可能发现不了。

新检查按实际已转换的Float32输入与参数建立精确参考。Float32是二进制有理数，可表示成有符号整数乘2^-149：

- QAVERAGE：对实际已接输入精确求和，除以实际数量后才舍入；未接端不补零。
- SUM：每路完整的`IN×GAIN+BIAS`及全部相加按整数表示计算，再与最终上下限后的原输出比较。未接可选路及其偏置不参与。
- POLYNOMIAL：以相同Float32输入和六项系数，精确计算0～5次各项的完整多项式，再舍入最终输出。

最终参考采用最近值、中点取偶数的binary32舍入；使用内置BigInt/DataView，无离线运行依赖。正常有限数范围仍按原合同检查，不能因为参考能算就越过已有溢出、次正规或其他模式拒绝。SUM在最后比较限幅后的输出：若限制后相同，隐藏的中间差别不改变输出，不新增误拦。

## 结果与兼容性

若原两项核对通过，但最终值与精确参考不同，诊断显示“精确求和/均值/多项式核对”，整拍不提交，连同上游变化一起回滚；失败记录可以复算。不是把数学参考当成控制器读数，也不开放质量/跟踪等其他模式。

|算法|当前模型|须重跑的旧完整记录|
|---|---|---|
|SUM|`ref1100-2006-sum-exact-check-v3`|原两路v1、四路v2|
|QAVERAGE|`ref1100-2006-qaverage-v2`|v1|
|POLYNOMIAL|`ref1100-2006-polynomial-v2`|v1|

普通工程无需新增参数，可以打开后按当前模型重新运行；其他算法模型不变。记录的engineVersion会反映实际引擎。

## 证据与边界

开发审查记录保存16项独立Python Fraction参考，以有理数精确距离选择相邻binary32结果，未使用模拟器输出作期望。另覆盖全部正常指数的首/次/末尾数及两种符号、中点、溢出边界、次正规参考值、均值除法、偏置、乘积低位和多项式幂。独立只读审查另核对4,800组混合符号/尺度向量，未发现重要差异。

工具内部将零规范为+0；与现有JSON和`===`比较合同一致，不提供有符号零位级保真。次正规数只可用于参考工具测试，仍不是当前模拟器开放的输入/中间结果。

数学公式参考建立在相同Float32输入/参数上，不能证明实际控制器的中间舍入、编译顺序、质量或启动行为。当前受限扫描及数值合同保持公开；有分歧时停止，不凭新增参考扩大支持范围。

## 有界开销测量

本机Ryzen7 9800X3D、Node24.20.0，4个整数输入源加196个SUM/QAVERAGE/POLYNOMIAL（66/65/65），运行1,000拍，前后1,001份完整快照一致。核心0.26.0约209.6ms，0.27.0约402.5ms（平均0.403ms/拍），新增检查有开销。报告`tmp/exact-sum-kernel-cost.json`保留运行文件SHA256；这是单次本机内核测量，不能当成完整UI、CPU节流或另一台普通电脑的结果。原0.33完整UI长测仍保留原版本边界。
